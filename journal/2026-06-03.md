## 二、核心架构

### 离线构建（一次性）

```
原始文档（PDF/MD/TXT）
  → 文档加载（DirectoryLoader）
  → 文本清洗（去水印、去Mermaid代码块、合并空行）
  → 文本切分（5种策略可选）
  → 向量化（千问 Embedding, 1536维）
  → 建立索引（FAISS + BM25）
  → 本地持久化（vector_store/）
```

### 在线检索（每次问答）

```
用户问题
  → 问题向量化（同一 Embedding 模型）
  → 双路并行检索（FAISS语义 + BM25关键词）
  → RRF 融合排名（倒数排名融合，k=60）
  → Reranker 精排（交叉编码器，qwen3-rerank）
  → Prompt 注入（4种模板自动选择）
  → LLM 流式生成（SSE 逐 token 推送）
  → 最终回答
```

### 代码文件职责

| 文件 | 职责 |
|------|------|
| `config.py` | 所有参数集中管理，三层级配置覆盖 |
| `knowledge_base.py` | 文档加载、向量化、双路检索、RRF、Reranker |
| `splitters.py` | 5种文本切分策略 |
| `llm_client.py` | 4种 LCEL 链 + 自动路由选择 |
| `prompts.py` | Prompt 模板、热重载、版本管理 |
| `web_search.py` | SearXNG 搜索 + 熔断器 + 指数退避 |
| `app.py` | Flask 路由、SSE 流式推送、对话历史管理 |
| `main.py` | CLI 命令行入口 |

## 三、各节核心知识点

### 01 · LLM 调用基础
- 大模型对外提供 OpenAI 兼容的 HTTP 接口
- LangChain 的 `ChatOpenAI` 封装了 `invoke`（等待完整回答）、`stream`（逐token输出）、`batch`（并行处理）
- 消息角色：`system`（系统指令）、`human`（用户输入）、`ai`（模型回复）

### 02 · 文本切分策略
- **固定字符切分**：最简单，但会切断句子
- **滑动窗口（Overlap）**：相邻 chunk 重叠避免边界截断，代价是存储量增加
- **递归字符切分**（生产推荐）：按优先级尝试分隔符（段落→换行→句号→空格→强制截断）
- 推荐参数：chunk_size 500~1200字，chunk_overlap 为 chunk_size 的 10%~20%

### 03 · Embedding 向量化
- Embedding 将文本转为高维向量（1536/3072维），语义相近的文本向量距离也近
- 向量检索可解决关键词匹配无法处理同义词的问题
- 余弦相似度衡量两向量方向相似程度，本项目阈值设 0.62
- 千问 Embedding 对中文专业术语优于通用英文模型
- 批处理：API 单次限制约 25 条，需要分批调用

### 04 · 向量数据库
- ChromaDB（入门）：轻量级，零配置，适合快速原型
- FAISS（生产）：Meta 开源，C++ 实现极快，支持 Flat/IVF/HNSW 多种索引
- FAISS 三种检索方式：`similarity_search`、`similarity_search_with_score`、`as_retriever` 带阈值过滤
- 本项目文档量较小，使用 Flat 索引即可

### 05 · 文档加载与解析
- PDF：处理换行断词、连字符、页码页眉污染；可用 pdfminer 或 LangChain PyPDFLoader
- DOCX：`python-docx` 提取段落文本
- 文本清洗：正则去除水印、Markdown 语法、Mermaid 代码块、多余空行
- 元数据：记录 source、page、section_title，用于检索后溯源展示

### 06 · BM25 关键词检索
- 向量检索弱于专有名词精确匹配（如模型名、版本号、参数名）
- BM25 是搜索引擎经典算法，由 IDF（逆文档频率）× TF（词频，有饱和上限）× 长度归一化组成
- 与向量检索互补：BM25 精准匹配关键词但不理解同义词，向量检索反之
- BM25 不需要 API，纯 CPU 计算，成本为零
- 可选依赖 `rank_bm25`，未安装时自动降级为单路 FAISS 检索

### 07 · 混合检索与 RRF 融合
- 两路检索结果评分量纲不同（余弦相似度 0~1 vs BM25 无上界），无法直接相加
- **RRF（倒数排名融合）**：不关心分数，只关心排名 — `RRF(d) = Σ 1/(k + rank(d))`
- k=60（原始论文推荐值）：平衡各排名权重，避免 rank1 主导
- 两路都命中的文档 RRF 分叠加排名靠前，单路命中文档排名靠后
- 去重键使用文档前 80 字，而非完整内容（高效且足够区分）

### 08 · Reranker 精排
- **双编码器（Bi-encoder）**= Embedding：文档和查询独立编码，可预计算，速度快但精度有限
- **交叉编码器（Cross-encoder）**= Reranker：查询和文档一起输入，精度高但无法预计算
- 两阶段检索：粗筛（FAISS+BM25，毫秒级）→ 精排（Reranker，百毫秒级）→ 送入 LLM（3~5条）
- 降级策略：Reranker API 出错时直接使用 RRF 结果，不影响主流程
- 精排只在候选数 > 1 时启用

### 09 · MultiQuery 检索扩写
- 用户口语化问题可能无法覆盖知识库中所有表述角度
- 用 LLM 将原始问题改写成 3 个不同角度的查询，并行检索后合并去重
- 代价：额外 1 次轻量 LLM 调用，增加 100~200ms 延迟
- `include_original=True` 确保原始问题检索结果不丢失
- 配置开关 `MULTI_QUERY_RETRIEVAL`，CLI 模式下自动退化为单次检索

### 10 · RAG 完整流程
- 相似度阈值（0.62）的必要性：FAISS 总会返回最相近的 k 条，无阈值时无关文档会污染上下文
- 4 种 Prompt 模式自动选择：KB_ONLY / DUAL_SOURCE / WEB_ONLY / GENERAL
- 对话引用检测：避免"你刚才说的…"这类问题无意义地检索知识库
- SSE 推送顺序：status → refs → token → done（让用户感知系统在积极工作）

### 11 · LCEL 链式编程
- `|` 管道语法：`chain = prompt | llm | parser`，数据从左向右流动
- 三组件：Prompt 模板（构建输入）、LLM（生成回答）、StrOutputParser（提取纯文本）
- 4 种链对应 4 种上下文场景，通过 `_pick()` 自动选择
- 模型热切换：重建 LLMClient 实例即可，代价极小

### 12 · Prompt 模板与提示词工程
- 把参考资料注入 system 消息而非 human 消息（LLM 对 system 遵循度更高）
- 正向指令优于负向约束："用自己的语言作答"比"禁止照搬"效果好
- 变量插值：`variables.json` + `{{变量名}}` 实现动态调整
- 热重载 + 版本管理：改 system.txt 后无需重启，可随时回滚
- Prompt 的三层结构：角色层 → 规则层 → 变量层

### 13 · SSE 流式输出
- SSE（Server-Sent Events）格式：`data: JSON\n\n`，前端用 EventSource 接收
- 5 种事件类型：status、refs、token、done、error
- **套话过滤**：缓冲 40 字符后正则过滤"根据知识库…"等开头套话
- **对话引用检测**：正则识别指代上文的提问，跳过检索直接走对话历史
- Markdown + LaTeX 渲染：先保存代码块和公式→渲染 Markdown→还原公式和代码块

### 14 · 对话历史管理
- 模型无状态，多轮对话需手动拼接历史消息
- Token 预算截取（MAX_HISTORY_TOKENS=3000）：从最新一轮往前保留，丢弃早期历史
- 精确计数用 tiktoken（cl100k_base 编码），不可用时降级为字符数/2 估算
- 历史由前端 localStorage 维护，后端无状态，易于横向扩展

### 15 · 5 种分块策略进阶
- **MarkdownHeadingSplitter**：按标题层级切分，超长时自动降级切割，适合结构化文档
- **RegexBoundarySplitter**：自定义正则匹配起始行，适合 Q&A 格式、编号条款
- **SemanticSplitter**（最智能）：用 Embedding 相似度骤降处找自然断点，适合无结构散文
- **RecursiveSplitter**：最终保底方案，按分隔符优先级递归切分
- **AutoSplitter**：自动探测文档结构（H3 > H2 > H4 > 编号 > 递归），至少 3 个匹配才认定结构有效
- 通过 `kb_config.json` 为每个知识库目录独立配置策略

### 16 · 网络搜索与熔断器
- SearXNG：开源元搜索引擎，自托管，免费无 API 限额
- **熔断器模式**：连续失败 N 次（阈值 3）→ 断开 → 等待恢复时间（60s）→ 半开尝试 → 成功闭合 / 失败重新断开
- **指数退避重试**：失败后等待 1s、2s、4s 再重试，给服务恢复时间，避免重试风暴
- 并行检索：KB 检索和网络搜索用 ThreadPoolExecutor 并行执行，互不等待

### 17 · Flask Web 服务设计
- RESTful API 路由：聊天、模型配置、知识库管理、提示词管理、健康检查
- **路径安全校验**：`realpath()` 解析后与知识库目录对比，防目录遍历攻击
- **异步重建**：后台线程 + 状态字典 + 前端轮询，防止阻塞 HTTP 请求
- 连接测试端点：临时测试新配置而不影响当前模型（温度0，max_tokens=32）
- 关键 API 设计：`/api/chat/stream`（SSE）、`/api/kb/rebuild`（异步）、`/api/prompts/reload`（热重载）

### 18 · 配置管理与工程实践
- **三层级配置**：代码默认值 ← .env 文件 ← model_config.json（越靠后优先级越高）
- API Key 安全：前端显示脱敏版（`sk-****...xxxx`），保存时识别脱敏版并保留原值
- **可选依赖的优雅降级**：dashscope/rank_bm25 缺失时系统仍正常运行
- **启动校验**：服务启动时立即验证必要配置，失败则退出，不等第一次请求
- Windows 编码处理：`sys.stdout.reconfigure(encoding='utf-8', errors='replace')`
- 单一职责：每个文件只做一件事，修改一个功能时只需改一个文件

### 19 · RAG 五大痛点与解决方案

| 痛点 | 现象 | 根因 | 解法 |
|------|------|------|------|
| **召回失败** | 内容存在但检索不到 | 标题被切掉/阈值过高/chunk太碎 | 标题写入chunk + 调低阈值 + 增大chunk_size |
| **忽视资料** | 检索到了但LLM不用 | context注入位置错/指令太弱 | 参考资料放system消息 + 强化指令措辞 |
| **回答死板** | 原文照搬无整合 | Prompt用词暗示"复制" | 明确"原材料→成品"定位 + Few-shot示例 |
| **上下文失忆** | 加了历史反而更差 | 引用检测覆盖不全/缺检索路由 | 扩充引用词库 + 增加智能路由判断 |
| **Prompt难管** | 改了无数版越改越差 | 缺乏迭代方法论 | 测试集 + A/B存档 + CoT + 分层结构 |

## 四、关键技术决策汇总

| 决策 | 取值 | 原因 |
|------|------|------|
| Embedding 模型 | 千问 text-embedding-v2（1536维）| 中文专业术语理解优于通用模型 |
| LLM 模型 | DeepSeek（OpenAI 兼容接口）| 中文能力强，性价比高 |
| 向量数据库 | FAISS | 速度快、与 LangChain 深度集成 |
| chunk_size | 500~1200 字 | 平衡信息完整性与检索精度 |
| 相似度阈值 | 0.62 | 过滤无关文档，可从 0.6 开始微调 |
| RRF k 值 | 60 | 原始论文推荐，实践稳健 |
| Reranker | qwen3-rerank（交叉编码器）| 精度远高于双编码器 |
| Token 预算 | 3000 | 保障上下文窗口内稳定运行 |
| 熔断阈值 | 连续失败 3 次，恢复期 60s | 防止失效服务拖垮主流程 |
